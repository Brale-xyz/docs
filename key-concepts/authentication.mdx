The Brale API uses Bearer Authentication and API keys to authenticate your requests. Tokens are short-lived (~60 minutes); refresh automatically using `expires_in`.

## API Keys

Your ability to authenticate to the API is granted through an API Key associated with an Application. Applications are specific to testnet or mainnet access, and have a specific set of permissions. You can create multiple API applications within the dashboard, each assigned specific API scopes. See [Environments](/overview/sandbox-and-testnet) for how testnet and mainnet differ.

## Scopes

Each permission you enable on an application grants one or more OAuth scopes. Every endpoint requires a specific scope. Requests made with a token that lacks the scope return `403 Forbidden`.

| Scope | Endpoints |
| --- | --- |
| `accounts:read` | `GET /accounts`, `GET /accounts/{account_id}`, `GET /accounts/{account_id}/verification/documents` |
| `accounts:write` | `POST /accounts`, `PATCH /accounts/{account_id}`, `POST /documents` |
| `addresses:read` | `GET /accounts/{account_id}/addresses`, `GET /accounts/{account_id}/addresses/{address_id}`, `GET /accounts/{account_id}/addresses/{address_id}/balance` |
| `addresses:write` | `POST /accounts/{account_id}/addresses/external` (bank and onchain), `POST /accounts/{account_id}/addresses/internal`, `PATCH /accounts/{account_id}/addresses/{address_id}` |
| `financial-institutions:read` | `GET /accounts/{account_id}/addresses/offchain`, `GET /accounts/{account_id}/addresses/offchain/{address_id}`, legacy `GET /accounts/{account_id}/financial-institutions` endpoints, `POST /accounts/{account_id}/financial-institutions/{fi_id}/update-link-token` |
| `financial-institutions:write` | `POST /accounts/{account_id}/addresses/offchain` (bank only), `PATCH /accounts/{account_id}/addresses/offchain/{address_id}`, `POST /accounts/{account_id}/plaid/*`, legacy `POST /accounts/{account_id}/financial-institutions/external`, `/register-account`, and `/plaid/link_token` |
| `transfers:read` | `GET /accounts/{account_id}/transfers`, `GET /accounts/{account_id}/transfers/{transfer_id}` |
| `transfers:write` | `POST /accounts/{account_id}/transfers` |
| `automations:read` | `GET /accounts/{account_id}/automations`, `GET /accounts/{account_id}/automations/{automation_id}`, `GET /accounts/{account_id}/wire-instructions` |
| `automations:write` | `POST /accounts/{account_id}/automations`, `PATCH /accounts/{account_id}/automations/{automation_id}`, `PATCH /accounts/{account_id}/automations/{automation_id}/destination` |
| `webhooks:read` | `GET /accounts/{account_id}/webhooks`, `GET /accounts/{account_id}/webhooks/{subscription_id}`, `GET /accounts/{account_id}/webhooks/event_types`, `GET /accounts/{account_id}/webhooks/deliveries` |
| `webhooks:write` | `POST /accounts/{account_id}/webhooks`, `PATCH` and `DELETE /accounts/{account_id}/webhooks/subscriptions/{subscription_id}` |

The OpenAPI details on each [API reference](/api-reference/brale-introduction) page list the exact scope that endpoint requires.

### Least-privilege payout key

`addresses:write` lets a key create both bank accounts and onchain addresses through `POST /accounts/{account_id}/addresses/external`. If a key only needs to register bank accounts for ACH, wire, or FedNow payouts, register them with [`POST /accounts/{account_id}/addresses/offchain`](/api-reference/brale/create-offchain-address) instead. That endpoint uses `financial-institutions:write` and cannot create onchain addresses.

Enable these permissions on a payout-only application:

| Dashboard permission | Scope | Used for |
| --- | --- | --- |
| Financial Institutions (create/update) | `financial-institutions:write` | Register the payout bank account with `POST /accounts/{account_id}/addresses/offchain` |
| Create/Update Transfers | `transfers:write` | Send the payout with `POST /accounts/{account_id}/transfers` |
| View Transfers | `transfers:read` | Check payout status with `GET /accounts/{account_id}/transfers/{transfer_id}` |
| View Addresses | `addresses:read` | Check the source balance with `GET /accounts/{account_id}/addresses/{address_id}/balance` |

Leave **Create/Update Addresses** (`addresses:write`) disabled so the key cannot add external onchain addresses.

## Obtain an Access Token

Brale uses OAuth2 with the `client_credentials` grant type for secure access to our APIs. Sending a request to the Auth endpoint will return a bearer token to be used on all subsequent calls. The response will include the number of remaining seconds that the token is valid before a new one will need to be retrieved.

The Authorization header uses Basic HTTP Authentication. This requires encoding your `client_id` and `client_secret` into a Base64 format.

To generate the Base64 encoded string, you can use a command-line tool like base64 or an online encoder. Ensure that your `client_id` and `client_secret` are separated by a colon `:` and then encoded. This encoded string will be used in the Authorization header.

```shell
curl --request POST \
  --url https://auth.brale.xyz/oauth2/token \
  --header 'Authorization: Basic ${BASE_64_OF(client_id:client_secret)}' \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data grant_type=client_credentials
```

## Authenticated Requests

Include the bearer token in the Authorization header of your API requests.

```shell
curl --request GET \
  --url https://api.brale.xyz/tokens \
  --header 'Authorization: Bearer OiVz67P7emAx0JUJRmYHP4pI-nSlYQn7ivTQE.A-tXeGnuzQBRSjq9QNGQXZ4aRl7Rbm8wY'
```

## Mutual TLS (mTLS)

For customers that want an additional layer of transport security, Brale offers mutual TLS. With standard TLS, only the server proves its identity. With mTLS, your client also presents a certificate, so both sides of the connection are authenticated before any request is processed. This ensures that only clients holding a valid certificate issued for your integration can reach your API endpoint, adding a strong network-level control on top of OAuth2 bearer token authentication.

mTLS is enabled per customer. When you request it, Brale provisions a dedicated mTLS-enabled API endpoint for your integration and works with you to create, install, and test client certificates against that endpoint. To get started, request mTLS through Brale support.

## Token Expiration

Access tokens are short-lived and expire ~60 minutes after issuance.

When a token expires:

- API calls will return a `401 Unauthorized` error.
- Your application should request a new token using the same client credentials before retrying the request.
- Best practice is to refresh automatically before expiry using `expires_in` and to retry idempotently after refresh.
